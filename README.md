# Airis Residence — сайт отеля

Новый сайт отеля Airis Residence (Алматы) 

```
airis_residence/
├─ frontend/        Next.js 16 · TypeScript · Tailwind 4 · Motion · Three.js
│  └─ app/(site)    публичный сайт
│  └─ app/admin     панель управления
├─ backend/         FastAPI · SQLAlchemy · SQLite/PostgreSQL
└─ docs/
   ├─ КОНСЬЕРЖ.md   ИИ-помощник: устройство, правила, задачи → передача разработчику
   ├─ EXELY_API.md  подключение API системы бронирования
   ├─ ИНТЕГРАЦИЯ.md инструкция для банка и поставщика бронирования
   └─ АДМИНКА.md    инструкция для администратора отеля
```

Запуск и проверки — двумя скриптами в корне:

```powershell
.\ЗАПУСТИТЬ.ps1        # поднять сайт и бэкенд локально
.\ПРОВЕРИТЬ.ps1 -Fast  # прогнать быстрые проверки
```

## ИИ-консьерж

Автоматический помощник, который переписывается с гостями от лица отеля:
отвечает про номера и цены, смотрит настоящее наличие в Exely, оформляет
брони, читает присланные платёжки и передаёт разговор человеку там, где не
должен решать сам. Русский, казахский, английский.

Смотреть и пробовать: админка → **Консьерж**. Каналы (WhatsApp, Instagram)
ещё не подключены — пока есть окно переписки в админке.

**Тому, кто продолжит работу над ним, — `docs/КОНСЬЕРЖ.md`.** Там устройство,
правила, о которые уже спотыкались, и список задач по убыванию пользы.

| Часть | Файл |
|---|---|
| Правила разговора и вызов модели | `backend/app/concierge.py` |
| Факты об отеле (единственный источник) | `frontend/app/api/knowledge/route.ts` |
| Системы бронирования, подменяемые | `backend/app/booking_system/` |
| Разбор платёжных документов | `backend/app/payment_docs.py` |
| Время отеля (Алматы, не UTC) | `backend/app/almaty.py` |

## Стек и почему он

| Слой | Технология | Причина |
|---|---|---|
| Фронтенд | **Next.js 16** (App Router, Turbopack) | Рендер на сервере → готовый HTML для поисковиков; SEO из коробки (метатеги, sitemap, structured data) |
| Стили | **Tailwind CSS 4** | Дизайн-система в одном файле `globals.css`, ноль лишнего CSS в бандле |
| Анимация | **Motion** + **Lenis** | Инерционный скролл и параллакс; всё отключается при `prefers-reduced-motion` |
| 3D | **React Three Fiber** + **drei** | Процедурная сцена в hero — ни одного внешнего ассета, грузится только в браузере |
| Картинки | `next/image` | AVIF/WebP, ленивая загрузка, нужный размер под экран |
| Бэкенд | **FastAPI** + SQLAlchemy (async) | Номера, заявки, загрузка фото, приём оплаты; автодокументация на `/docs` |
| База | SQLite → PostgreSQL | Для старта хватает файла, переезд — сменой одной строки |
| Фото | **Pillow** | Сжатие и поворот загруженных снимков на сервере |

## Запуск

### Фронтенд

```bash
cd frontend
cp .env.example .env.local     # заполнить при необходимости
npm install
npm run dev                    # http://localhost:3000
npm run build && npm start     # прод-сборка
```

### Бэкенд

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate         # Windows
pip install -r requirements.txt
cp .env.example .env           # заполнить
uvicorn app.main:app --reload  # http://localhost:8000/docs
```

Бэкенд не обязателен: без него заявки уходят в Telegram напрямую из Next.js
(`app/api/leads/route.ts`), а номера берутся из `lib/site.ts`. Бэкенд нужен
для админки, базы заявок и онлайн-оплаты.

## Админ-панель

Адрес: **`/admin`**. Через неё меняются цены, тексты, фотографии и порядок
номеров, а также разбираются заявки. Инструкция для администратора отеля —
[docs/АДМИНКА.md](docs/АДМИНКА.md), её можно передать сотруднику как есть.

### Что нужно, чтобы она заработала

В `backend/.env`:

```bash
ADMIN_USERNAME=admin
ADMIN_PASSWORD=<придумать пароль>
SECRET_KEY=<python -c "import secrets; print(secrets.token_urlsafe(48))">
PUBLIC_MEDIA_BASE=https://<адрес-бэкенда>   # из него строятся ссылки на фото
```

В `frontend/.env.local`:

```bash
BACKEND_URL=https://<адрес-бэкенда>
```

Пока `ADMIN_PASSWORD` или `SECRET_KEY` пустые, админка закрыта целиком —
не «пускает с пустым паролем», а отвечает, что не настроена.

### Как устроена безопасность

- Одна учётная запись на отель — база пользователей тут была бы лишней.
- Пароль сверяется в постоянном времени, после 10 неудачных попыток с одного
  адреса вход блокируется на 5 минут.
- Токен сессии подписан HMAC и лежит в **httpOnly-куке**: скрипты на странице
  до него не дотягиваются, украсть через XSS нельзя.
- Браузер общается только со своим доменом через прокси `/api/admin/*` —
  бэкенд не обязан быть открыт наружу.
- `/admin` закрыт от индексации в `robots.txt` и мета-тегом.

### Фотографии

Загруженные снимки ужимаются до 2200 px по ширине и переводятся в WebP:
кадр с телефона на 6 МБ превращается в ~150 КБ. Учитывается EXIF-поворот,
поэтому «боком» ничего не ложится.

> ⚠️ **Файлы лежат на диске бэкенда** (`UPLOAD_DIR`). На Railway, Render и
> подобных площадках файловая система стирается при каждом деплое — нужно
> примонтировать постоянный диск и указать путь к нему, иначе фотографии
> пропадут после ближайшего обновления. Альтернатива на будущее — S3/R2.

### Откуда сайт берёт номера

`lib/rooms.ts` — единственная точка входа:

| Условие | Источник |
|---|---|
| `BACKEND_URL` задан, бэкенд отвечает | база (то, что в админке) |
| бэкенд не отвечает или адрес не задан | `lib/site.ts` — запасной список |

Запасной список существует ровно для того, чтобы сайт не падал из-за
админки: упал сервер с базой — гость всё равно видит номера и цены.
Проверено: при остановленном бэкенде все страницы отдают 200.

**Публичные страницы рендерятся на каждый запрос, без кэша.** Пробовали ISR
с тегами — цена менялась в базе, а посетитель ещё какое-то время видел
старую: Next отдаёт устаревшую страницу и лишь запускает пересборку в фоне,
момент её готовности не контролируется. Для админки это выглядит как
«сохранил, а на сайте по-старому». Один запрос к своему же бэкенду
(миллисекунды) — приемлемая плата за то, что сайт всегда совпадает
с админкой.

## Что где лежит

| Файл | Зачем |
|---|---|
| `frontend/lib/site.ts` | Адрес, телефоны, реквизиты, условия проживания + **запасной список номеров** на случай недоступности бэкенда |
| `frontend/lib/rooms.ts` | Откуда сайт берёт номера: база или запасной список |
| `frontend/lib/booking.ts` | Единственная точка, через которую сайт узнаёт ссылку на бронирование |
| `frontend/lib/seo.ts` | Метатеги и structured data (Hotel, HotelRoom, FAQ, BreadcrumbList) |
| `frontend/lib/faq.ts` | Вопросы-ответы (используются и в вёрстке, и в разметке FAQPage) |
| `frontend/app/globals.css` | Дизайн-система: цвета, тени, типографика, утилиты |
| `frontend/components/booking/BookingWidgetSlot.tsx` | Место под виджет банка |
| `frontend/components/sections/Tour3D.tsx` | Место под 3D-тур |
| `backend/app/payments.py` | Каркас интеграции с эквайрингом |

### Как поменять цену или описание номера

Через админку на `/admin` — правки видны на сайте сразу, пересобирать
ничего не нужно.

Если бэкенд не поднят, номера правятся в коде: `frontend/lib/site.ts`,
массив `rooms`, затем пересборка.

## Фотографии

Все фото перенесены с текущего сайта в `frontend/public/images/`:

```
images/
├─ hotel/       лобби, ванные комнаты, детали интерьера
├─ rooms/       по папке на тип номера
└─ breakfast/   завтраки
```

> ⚠️ Фото разложены по типам номеров по визуальному признаку.
> Категории **Comfort** и **Luxe** стоит перепроверить: если фото
> перепутаны, достаточно переименовать файлы в папках или поправить
> список `images` у номера в `lib/site.ts`.

Стоковые картинки со старого сайта (фото с ресепшена «HOTEL», интерьер
из Unsplash) намеренно **не перенесены** — на новом сайте только
настоящие фото отеля.

## Что сделано для SEO

- Уникальные `title` и `description` на каждой странице, канонические ссылки
- Разметка schema.org: `Hotel` (с адресом, координатами, ценами, удобствами),
  `HotelRoom` для каждого номера, `FAQPage`, `BreadcrumbList`
- `sitemap.xml` и `robots.txt` генерируются автоматически — **на старом
  сайте их не было вообще**
- Open Graph и Twitter Card с готовой картинкой `public/og.jpg`
- Семантическая структура: один `h1` на страницу, осмысленные `h2`/`h3`
- Все изображения с осмысленным `alt`, включающим тип номера и город
- Адрес, телефоны и часы работы продублированы текстом (не картинкой) —
  это то, что читают поисковики для локальной выдачи
- Отдельные страницы под каждый тип номера — пять точек входа из поиска
  вместо одной

### Что нужно сделать после запуска

1. Подтвердить сайт в Google Search Console и Яндекс.Вебмастере, отправить sitemap.
2. Сверить адрес и телефоны с карточками 2ГИС, Google Business и Яндекс.Бизнес —
   **символ в символ**, иначе локальное SEO разваливается.
3. Уточнить координаты в `lib/site.ts` (`address.lat` / `address.lng`) по карточке 2ГИС.
4. Отдать оферту и политику конфиденциальности юристу — в файлах стоят пометки-черновики.
5. Подключить аналитику (Google Analytics или Яндекс.Метрику).

## Домен и деплой

Домен `airisresidence.kz` зарегистрирован на hoster.kz, хостинг — тариф
Эконом-2 с Plesk.

**Рекомендуемый вариант — Vercel:**

1. Залить `frontend/` в git-репозиторий, подключить его к Vercel.
2. Прописать переменные окружения из `.env.example` в настройках проекта.
3. В кабинете hoster.kz в DNS домена изменить A-запись `@` и CNAME `www`
   на значения, которые выдаст Vercel.
4. SSL Vercel выпустит сам.

Старый сайт на WordPress **не удалять**, пока новый не заработает на домене.
Пароль от админки WordPress для переезда не нужен — домен управляется
из кабинета hoster.kz.

Бэкенд разворачивается отдельно — Railway, Render или любой VPS.
Shared-хостинг Эконом-2 Python не выполняет.

⚠️ Раз админка хранит фотографии на диске бэкенда, площадка должна давать
**постоянный диск**. На бесплатных тарифах Railway/Render файловая система
эфемерная — фотографии переживут работу сайта, но не переживут деплой.
