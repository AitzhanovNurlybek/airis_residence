# Присмотр за ботом: что проверяется само и куда приходят тревоги

С 2026-10-05. Повод: 4 октября бот сутки не отвечал гостям — закончился
бесплатный тариф Green API, — и узнали об этом по жалобе.

## Ежедневная проверка

Каждое утро в 09:00 по Алматы GitHub запускает «Ежедневная проверка бота»
(`.github/workflows/daily-check.yml` → `POST /api/webhooks/daily-check`).
Только чтение, гостям ничего не уходит. Проверяется:

| Что | Почему |
|---|---|
| WhatsApp-номер авторизован, адрес вебхука на месте, входящие и звонки включены | Сброс любого из них — бот молчит |
| За сутки не было упора в лимит тарифа и неушедших ответов | Так было 4 октября |
| Модель принимает запросы (бесплатный подсчёт токенов) | Кончились деньги на ключе или сменилось имя модели |
| Ключ распознавания голосовых принимается | Иначе на каждое голосовое — «не распознаю» |
| Exely отдаёт наличие, справка грузится с сайта | Без них бот не назовёт ни цены, ни свободных номеров |
| Уведомления отелю настроены | Иначе они уходят в «сообщение себе» |

Если что-то не так:
1. разработчику приходит сообщение в WhatsApp (`DEV_ALERT_PHONE`) и в
   Telegram (`DEV_TELEGRAM_CHAT_ID`);
2. запуск в GitHub краснеет — GitHub присылает письмо. Этот канал не зависит
   от WhatsApp и сработает, даже когда сломан сам WhatsApp.

Проверить вручную в любой момент: GitHub → Actions → «Ежедневная проверка
бота» → Run workflow. Или полная проверка с компьютера:
`backend\proverka_nomera.py` (15 пунктов, никому ничего не отправляет).

## Куда приходят тревоги

| Событие | Ресепшн (`LEAD_NOTIFY_PHONE`) | Разработчик |
|---|---|---|
| Новая бронь, заявка с сайта, просьба об отмене | да | — |
| Просьба живущего гостя (сменить номер, поздний выезд, поломка) | да | — |
| Пропущенный WhatsApp-звонок на номер бота | да | — |
| Ответ гостю не ушёл | да | да, копией |
| Ежедневная проверка нашла проблему | — | да + письмо GitHub |

## Telegram — запасной канал разработчика

Один раз, ~5 минут:
1. В Telegram: @BotFather → `/newbot` → имя → получить токен.
2. Токен — в `backend/.env` строкой `TELEGRAM_BOT_TOKEN=...`.
3. Написать своему боту любое сообщение.
4. `backend\.venv\Scripts\python.exe telegram_chat_id.py` — найдёт чат,
   пришлёт проверочное сообщение и напечатает, что вписать в Vercel:
   `TELEGRAM_BOT_TOKEN` и `DEV_TELEGRAM_CHAT_ID`. Затем Redeploy.

`TELEGRAM_CHAT_ID` (без `DEV_`) — другой чат: туда идут заявки с сайта.
Не путать.

## Модель бота

На какой модели отвечает бот — видно в `/api/backend/health`
(`concierge_model`). Задаётся переменной `CONCIERGE_MODEL` в Vercel; если её
нет — значение по умолчанию в `backend/app/config.py` (`claude-sonnet-5`, выбрано 2026-10-05).
Сравнение моделей 2026-10-05 и цена ответа — там же, в комментарии.

## Сотрудник в чате

Если сотрудник пишет гостю сам с телефона отеля, бот в этом чате молчит
30 минут после последнего сообщения сотрудника (`STAFF_PAUSE_MINUTES` в
Vercel, по умолчанию 30 — так попросил ресепшн). Реплики гостя за это время и слова сотрудника
ложатся в историю, поэтому бот, вернувшись, знает, о чём договорились. Дожим
в такие чаты не пишет двое суток.

Работает, только пока в Green API включено `outgoingMessageWebhook = yes`
(уведомления об исходящих с телефона; включено 2026-10-05). Ежедневная
проверка сообщит, если настройку выключат. Автоответы WhatsApp Business
(приветствие, «нет на месте») на телефоне отеля должны быть выключены: бот
примет их за сотрудника и замолчит.

## Цены на сайте

Цены номеров на сайте (и в справке бота) берутся из Exely каждое утро —
шаг «Цены сайта — как в Exely» в `daily-check.yml`, код —
`backend/app/price_sync.py`. Берётся обычная цена Exely (без скидки тарифа)
на ближайшую дату, на которую номер продаётся: цены в Exely сезонные, и сайт
показывает то, что гость увидит сейчас. Менять цены нужно в Exely — правка в
админке продержится до утра. Проверить, что изменится:
`POST /api/backend/api/webhooks/sync-prices?dry_run=1` с ключом `X-Api-Key`.

Booking.com продаёт номера по ценам Exely плюс 12,5% (сверено 2026-10-05):
на сайте отеля напрямую дешевле.
