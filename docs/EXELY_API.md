# Подключение API Exely

Что даёт API, чего он не даёт, что включить в кабинете и как из-за этого
меняется работа ИИ-консьержа.

Обновлено 2026-08-25 — после чтения документации на `exely.com/dev-portal`.

---

## Главный вывод: бронь через API создать нельзя

Прочитана вся документация разработчика. **Ни один из семи публичных API не
создаёт бронь.** Это не пробел в документации и не вопрос прав доступа — такого
метода в Exely Connect просто нет.

Есть `POST`-методы, и они сбивают с толку при беглом взгляде. Но все они —
либо поисковые запросы, либо операции над **уже существующей** бронью:

| Метод | Что на самом деле делает |
|---|---|
| `POST /v1/properties/room-stays/search` | ищет варианты размещения, ничего не создаёт |
| `POST .../reservations/{n}/check-in` | отмечает заезд по существующей брони |
| `POST .../reservations/{n}/payment` | проводит платёж по существующей брони |
| `POST .../reservations/{n}/assign-rooms` | назначает комнату существующей брони |
| `POST /corporates` | заводит корпоративного клиента, не бронь |

Это ровно то, о чём говорила Аида: **«апи есть, единственное условие — она
должна вести гостей на нашу форму бронирования»**. Условие не про вежливость,
а про устройство системы: бронь рождается только в форме Exely.

**Значит, ИИ-консьерж не будет ставить бронь сам.** Он доводит гостя до формы
с уже подставленными датами и номером.

## Что API всё-таки даёт — и это много

### 1. Настоящее наличие и цены, но по договору

Сейчас мы читаем наличие с адреса, который подсматриваем у виджета
(`kz-ibe.hopenapi.com`). Он недокументированный: может измениться в любой день
без предупреждения, и мы узнаем об этом по упавшему консьержу.

**Search API** даёт то же самое официально:

```
POST /v1/properties/room-stays/search       поиск по нескольким объектам
GET  /v1/properties/{propertyId}/room-stays наличие конкретного отеля
POST /v1/properties/{propertyId}/services   дополнительные услуги
POST /v1/properties/{propertyId}/extra-stays ранний заезд и поздний выезд
```

Переезд на них снимает главный риск нынешней схемы.

### 2. Настоящие брони гостей — этого у нас нет вообще

**Read Reservation API**:

```
GET /v1/properties/{propertyId}/bookings           список броней
GET /v1/properties/{propertyId}/bookings/{number}  одна бронь целиком
```

Плюс **PMS API** — поиск по гостю, история проживаний, счета:

```
GET  /v2/.../reservations/search              поиск по датам
GET  /v2/.../reservations/{number}            бронь целиком
GET  /v2/.../guests/search                    гость по имени, телефону, номеру
GET  /v2/.../guests/{id}/stays                история проживаний
GET  /v2/.../reservations/{number}/invoices   счета по броне
```

Это меняет консьержа качественно. Сегодня на «какая у меня бронь?» он смотрит
только в нашу песочницу. С этим — отвечает по настоящей броне: даты, номер,
статус, сумма. Гость пишет в час ночи «во сколько заезд по моей броне» и
получает ответ, а не «позвоните утром».

### 3. Уведомления о брони (вебхуки)

В кабинете при создании подключения есть вкладка **«Вебхуки»** —
автоматические уведомления о создании и отмене брони.

Это то, что склеивает схему. Консьерж дал гостю ссылку → гость оформил в форме
Exely → вебхук сообщил нам → консьерж продолжает разговор уже зная номер
брони. Со стороны гостя выглядит как одна беседа, хотя бронь он оформил сам.

### 4. Правила отмены и питание — из первых рук

**Content API**:

```
GET /v1/properties/{propertyId}/cancellation-rules  условия отмены
GET /v1/properties/{propertyId}/extra-stay-rules    ранний заезд, поздний выезд
GET /v1/meal-plans                                  планы питания
GET /v1/room-type-categories                        категории номеров
```

Сейчас условия отмены консьерж берёт из ответа виджета. Здесь то же самое
официально.

### 5. Корпоративные клиенты

**Reference Data API**:

```
POST /corporates                 завести корпоративного клиента
GET  /corporates/{corporateId}   получить его данные
```

Стоит изучить отдельно, когда дойдут руки: возможно, корпоративные брони
получится помечать в шахматке как принадлежащие конкретной компании. Сейчас
менеджер вносит их вручную и связь с компанией живёт только у нас.

## Что включить в кабинете

Кабинет → **Настройки гостиницы** → **Подключения API** → **Создать
подключение**.

На вкладке «Публичные API» отметить:

| API | Зачем | Нужен |
|---|---|---|
| **Search API** | наличие и цены — заменит подсмотренный адрес | обязательно |
| **Read Reservation API** | настоящие брони гостей в переписке | обязательно |
| **Content API** | условия отмены, питание, категории | обязательно |
| **PMS API** | поиск гостя, история, счета | желательно |
| **Reference Data API** | корпоративные клиенты | позже |
| PMS Analytics API | статистика загрузки | не нужен |
| PMS Integration Storage API | инвентарь без данных гостей | не нужен |

На вкладке **«Вебхуки»** включить уведомления о **создании** и **отмене**
брони.

Авторизация — OAuth 2.0: выдадут `client_id` и `client_secret`, по ним
`POST /auth/token` возвращает токен для заголовка `Authorization: Bearer`.

Ключ показывают один раз — сразу в менеджер паролей.

## Как меняется работа консьержа

**Было задумано:** гость просит забронировать → консьерж сам создаёт бронь.
Так не выйдет.

**Как будет:**

1. Гость пишет в WhatsApp: «нужен номер на 12–15 сентября».
2. Консьерж смотрит наличие и цены (Search API) и отвечает по делу — что
   свободно, почём, с завтраком или без, какие условия отмены.
3. Гость выбирает. Консьерж присылает **ссылку на форму Exely с уже
   подставленными датами, категорией и тарифом** — гостю остаётся ввести имя
   и подтвердить.
4. Гость оформляет. Приходит вебхук.
5. Консьерж пишет: «Бронь оформлена, номер такой-то. Заезд с 14:00,
   завтрак включён». Дальше отвечает по этой броне через Read Reservation API.

Один шаг гость делает сам. Взамен: данные карты и персональные данные никогда
не проходят через нас, а бронь сразу и по-настоящему стоит в шахматке — без
ручного переноса менеджером.

### Что придётся сделать в коде

- `booking_system/exely.py` — перевести чтение наличия с подсмотренного адреса
  на Search API, добавить OAuth-токен;
- новый метод «собрать ссылку на форму брони» с датами и категорией;
- приём вебхука о создании и отмене брони;
- `find_booking` в консьерже — искать в настоящих бронях, а не только в
  песочнице;
- у консьержа убрать `create_booking` в режиме `exely` — он не должен обещать
  того, чего не может.

Место под всё это уже размечено: `backend/app/booking_system/` — один
интерфейс и подменяемые реализации.

## Чего API не даёт вообще

- **создать бронь** — только через форму;
- **изменить даты существующей брони** — метода нет, это к менеджеру;
- **отменить бронь** — метода нет; отмена либо через форму по ссылке из письма
  гостю, либо руками в кабинете;
- **выставить счёт компании** — счета Exely не выставляет, у нас свой печатный.
